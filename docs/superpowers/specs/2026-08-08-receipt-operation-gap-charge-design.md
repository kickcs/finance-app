# Сбор по операции: разница между суммой банка и суммой чека

**Дата:** 2026-08-08
**Статус:** дизайн утверждён

## Задача

Пользователь сканирует чек к операции, импортированной из Telegram. Банк списал 300 000, чек
на 290 000. Сейчас создаётся транзакция на сумму чека — баланс счёта врёт на 10 000.

Разница должна попасть в чек строкой-сбором, чтобы транзакция равнялась тому, что списал банк.

## Как работает сейчас

- `ImportConfirmPage.toScanReceipt()` уводит на `/scan-receipt?importedId=…&expectedAmount=300000`
- Мастер собирает позиции и сборы, `useSubmitStep` создаёт **одну** транзакцию на `totalAmount`
  (сумма чека) и помечает импорт подтверждённым
- Расхождение больше 1% показывается жёлтой плашкой на шаге 4 — и никак не устраняется

## Решение

Разница добавляется **строкой в блок сборов чека**, а не отдельной транзакцией. Транзакция
остаётся одна, на сумму банка, в категории магазина.

Следствие, принятое сознательно: сбор распределяется по участникам пропорционально их долям —
как «Обслуживание». Если чек делят трое, каждый доплачивает свою часть сбора.

### Правила

| Условие | Поведение |
|---|---|
| Чек меньше суммы банка | Строка «Сбор по операции» на разницу, итог = сумме банка |
| Чек больше суммы банка | Строки нет. Остаётся нынешняя жёлтая плашка на шаге 4 |
| Подытог = 0 (нет позиций) | Строки нет — иначе сбор был бы равен всей сумме операции |
| Валюта чека ≠ валюты операции | Строки нет — разница между разными валютами бессмысленна |
| Открыт не из импорта | Строки нет, всё как раньше |

Сумма сбора — **живой остаток**: `сумма банка − подытог − остальные сборы`. Правка позиций
пересчитывает её на лету, итог чека всегда равен списанию банка.

**Ручная правка отключает автопересчёт навсегда.** Пользователь поправил сумму, выключил
тумблер или удалил строку — с этого момента авто-сбор не вмешивается. Это «умный дефолт до
первого касания».

## Архитектура

Всё во фронте, слайс `features/scan-receipt`. Бэкенд не трогаем: транзакция и так создаётся
на `totalAmount`, а он теперь равен сумме банка.

```
ScanReceiptPage ──expectedOp{amount,currency}──► useReceiptWizard ──► useItemsStep
                                                                          │
                                     userCharges  (ref, пользовательские) ┤
                                     gapCharge    (computed, остаток)     ┤
                                                                          ▼
                                                        charges (computed) ──► всё остальное
```

### Виртуальный сбор вместо записи в массив

`charges` перестаёт быть `ref` и становится `computed`. Пользовательские сборы уезжают в
приватный `userCharges`, сбор по операции подмешивается сверху:

```ts
const gapCharge = computed<AmountReceiptCharge | null>(() => {
  if (gapDismissed.value) return null;
  const op = expectedOp();
  if (!op || op.amount <= 0 || op.currency !== currency.value) return null;
  if (subtotal.value <= 0) return null;
  const gap = op.amount - subtotal.value - userChargesAmount.value;
  return gap > 0
    ? { id: GAP_CHARGE_ID, label: 'Сбор по операции', type: 'amount', amount: gap, enabled: true }
    : null;
});

const charges = computed(() =>
  gapCharge.value ? [...userCharges.value, gapCharge.value] : userCharges.value,
);
```

Почему computed, а не запись в `charges` по watcher'у:

- Живой пересчёт получается бесплатно, без обратной записи в тот же ref
- Нет цикла реактивности: `gapCharge` читает `userCharges`, но не пишет в них
- «Пользователь поправил» и «watcher поправил» остаются различимы — иначе правило про
  отключение автопересчёта пришлось бы эмулировать флагами поверх watcher'а

Проверка арифметики: `totalAmount = subtotal + chargesAmount = subtotal + userChargesAmount +
(op.amount − subtotal − userChargesAmount) = op.amount`.

### Почему пропсы не меняются

`charges` спускается пропсом в `Step2EditItems`, `Step3AssignParticipants`, `Step4Summary`,
`AddChargeSheet`, `ShareLinkSheet`, `AssignableItemRow`. Подмена ref на computed с тем же именем
означает, что вся цепочка — включая `chargesAmount`, `totalAmount`, `getItemWithChargesTotal`,
доли участников и шаринг чека — получает сбор без единой правки пропсов.

### Материализация при ручной правке

`GAP_CHARGE_ID` — константа, а не `uid()`. Когда пользователь правит сумму, строка копируется
в `userCharges` **с тем же id**, и поднимается `gapDismissed`:

```ts
function materializeGapCharge(patch: Partial<AmountReceiptCharge>) {
  const gap = gapCharge.value;
  if (!gap) return;
  userCharges.value.push({ ...gap, ...patch });
  gapDismissed.value = true;
}
```

Стабильный id важен: `ChargeRow` в списке имеет `:key="charge.id"`. Смени id при
материализации — Vue пересоздаст строку, поле ввода потеряет фокус на первом же нажатии клавиши.

Разводка по действиям:

| Действие | Поведение |
|---|---|
| `updateChargeAmount(GAP_CHARGE_ID, x)` | Материализуется с суммой `x` |
| `toggleCharge(GAP_CHARGE_ID)` | Материализуется выключенной; повторный тумблер включает её обычным путём |
| `removeCharge(GAP_CHARGE_ID)` | `gapDismissed = true`, строка исчезает насовсем |
| `updateChargePercent(GAP_CHARGE_ID, …)` | No-op: сбор всегда типа `amount` |

Отказ живёт ровно до следующего чека: `setOcrTotalAmount` гасит `gapDismissed` там же, где уже
гасит `mismatchDismissed`. Пользователь, убравший сбор и переснявший чек, получает новый расчёт —
прежний отказ относился к прежним позициям. Восстановление черновика ставит флаг после этого
вызова, поэтому сохранённый выбор переживает перезагрузку страницы.

Вместе с флагом сбрасывается и **замороженная копия**: `setOcrTotalAmount` выкидывает строку с
`GAP_CHARGE_ID` из `userCharges`. Без этого сценарий «восстановил черновик с правленым сбором →
вернулся на шаг 1 → ручной режим» оставлял бы в списке две строки с одним id — дубль `:key`
ломает патчинг Vue, а `toggleCharge` попадал бы только в первую из них.

### Передача суммы операции

`ImportConfirmPage.toScanReceipt()` дополнительно кладёт в query `expectedCurrency`.
`ScanReceiptPage` собирает из query единый объект:

```ts
const expectedOp = computed<{ amount: number; currency: string } | null>(...)
const expectedAmount = computed(() => expectedOp.value?.amount ?? null)  // для плашки на шаге 4
```

`useItemsStep` принимает `expectedOp: () => {amount, currency} | null = () => null` — существующие
вызовы без аргумента продолжают работать.

### Черновик

`useReceiptDraft` сохраняет **`userCharges`**, а не `charges` — иначе виртуальный сбор осел бы в
localStorage и при восстановлении сложился бы с пересчитанным, удвоив разницу. Добавляется поле
`gapDismissed?: boolean`.

Версию схемы (`v: 1`) не поднимаем: поле опциональное с дефолтом `false`, а у старых черновиков
`charges` и так содержит только пользовательские сборы.

### Сверка с итогом чека из OCR

`totalMismatch` (плашка «позиции дают X, а в чеке итог Y» на шаге 2) сравнивала `totalAmount`
с напечатанным итогом. Как только авто-сбор поднимает `totalAmount` до суммы банка, эта плашка
загорелась бы всегда — 300 000 против 290 000.

Поэтому сверка считается от `subtotal + userChargesAmount`, без сбора по операции. Она отвечает
на вопрос «сошлись ли прочитанные строки с напечатанным итогом», а банковская разница к нему
отношения не имеет. Без суммы операции поведение прежнее: сбора нет, и обе суммы совпадают.

### UI

`ChargeRow` получает опциональный проп `auto?: boolean` — маленькая метка «авто» у ярлыка.
Без неё в чеке появляется строка, которую пользователь не добавлял, и это читается как баг.

Помечается она по `autoChargeId` (`gapCharge.value?.id ?? null`), а **не** сравнением с
`GAP_CHARGE_ID`: замороженная копия намеренно сохраняет тот же id, поэтому сравнение с константой
оставляло бы бейдж на строке, которая уже перестала пересчитываться, — метка врала бы ровно в тот
момент, когда её смысл меняется на противоположный. Заодно `GAP_CHARGE_ID` не утекает в UI-слой.

Жёлтая плашка на шаге 4 не трогается: пока авто-сбор активен, `totalAmount` равен
`expectedAmount` и плашка молчит сама. Она срабатывает ровно в двух оставшихся случаях —
чек больше банка и сбор отключён вручную.

## Обработка ошибок и краевые случаи

- **`expectedAmount` не парсится** — уже отфильтровано в `ScanReceiptPage` (`Number.isFinite`
  и `> 0`), приходит `null`, сбор не появляется
- **Пользователь дошёл до шага 3-4 и вернулся править позиции** — доли участников computed,
  пересчитаются вместе со сбором
- **«Платил не я»** — недостижимо: `payerLocked` включён при наличии `importedId`, транзакция
  в этом сценарии всегда моя
- **Ручной режим без фото** — покрыт правилом `subtotal > 0`: пока пользователь не ввёл ни одной
  позиции, сбора нет; дальше он работает как в OCR-режиме
- **Округление** — `gap` считается вычитанием целых, промежуточных делений нет.
  `calcLineTotalWithCharges` уже округляет доли через `Math.round`

## Тестирование

Тесты кладём в существующий `useReceiptWizard.spec.ts`, блоком
`describe('useItemsStep — сбор по операции')`: там уже есть `mountComposable` и мок хаптики,
а отдельный файл потребовал бы копию этой обвязки.

1. Без `expectedOp` — `charges` равен пользовательским, регрессии нет
2. Банк 300 000, позиции 290 000 → сбор 10 000, `totalAmount` 300 000
3. Позиции правятся до 296 000 → сбор сам становится 4 000, итог держится на 300 000
4. Чек больше банка (310 000) → сбора нет, итог 310 000
5. Подытог 0 → сбора нет
6. Валюта чека ≠ валюты операции → сбора нет
7. Пользовательский сбор 5 000 + позиции 290 000 → gap 5 000, итог 300 000
8. `updateChargeAmount(GAP_CHARGE_ID, 7000)` → материализация, автопересчёт замолкает
9. `removeCharge(GAP_CHARGE_ID)` → сбор не возвращается после правки позиций
10. `toggleCharge(GAP_CHARGE_ID)` → выключенная копия; повторный тумблер возвращает итог к 300 000
11. `getItemWithChargesTotal` распределяет сбор пропорционально долям
12. Новый снимок после ручного отказа возвращает авто-сбор (через `useReceiptWizard`, с моком OCR)
13. `autoChargeId` становится `null` после ручной правки — бейдж «авто» гаснет вместе с пересчётом
14. После сброса в ручной режим строка с `GAP_CHARGE_ID` остаётся в единственном экземпляре

Регрессия: остальные тесты `useReceiptWizard.spec.ts` и `useReceiptDraft.spec.ts` должны пройти
без правок ожиданий — черновик меняет только состав сохраняемых полей.

## Известное ограничение

Черновик сохраняет `totalAmount` **вместе** со сбором, а сам сбор выводится из `route.query`.
Открыв `/scan-receipt` кнопкой из «Новой операции», а не из импорта, пользователь увидит баннер
«Продолжить прошлый чек?» с суммой 300 000, а восстановит чек на 290 000. Честное решение —
класть `expectedOp` в черновик, но это решение о составе черновика, а не правка этой фичи;
`importedId` вырождается там ровно так же и давно.

## Что НЕ делаем

- Отдельную транзакцию «Комиссия» — отвергнуто в пользу строки внутри чека
- Отрицательный сбор, когда чек больше банка — механизм `charges` не рассчитан на минус,
  доли участников уехали бы в отрицательные значения
- Правки на бэкенде — `feeAmount` в `CreateTransactionCommand` остаётся только для переводов
