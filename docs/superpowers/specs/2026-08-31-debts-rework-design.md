# Переработка долгов: логика, данные, экраны

**Дата:** 2026-08-31
**Бриф:** «полностью переработать экраны долгов, логику и взаимодействие, не заводить
костылей, писать максимально переиспользуемый код, UI можно не сильно менять»

Долги — самая наращиваемая часть приложения: 18 коммитов за четыре месяца, каждый
добавлял действие (зачёт, отмена закрытия, редактируемые поля, комиссия, шаринг,
закрытие всех, шторка платежа). Наращивали, не переставляя фундамент, и фундамент
поехал. Эта спека описывает, куда его переставить.

UI сохраняется. Меняются границы: кто владеет правилом, кто владеет данными, кто
владеет состоянием экрана.

---

## 1. Корень: правило долга живёт в клиенте

`PATCH /debts/:id` принимает свободный набор полей, включая производные:
`remainingAmount`, `isClosed`, `forgivenAmount`, `closeTransactionId`
(`backend/src/modules/debt/presentation/dto/update-debt.dto.ts:15-96`).

Значит правило «платёж уменьшает остаток; остаток в ноль закрывает долг; прощение
обнуляет остаток наравне с оплатой» живёт не в домене, а во фронтенде: клиент сам
считает новый остаток, сам решает, закрылся ли долг, сам создаёт транзакцию и
отдельным запросом патчит долг. `usePartialPayment` — 266 строк именно этой
оркестрации (`frontend/src/features/partial-payment/model/usePartialPayment.ts:35-266`).

Агрегат при этом умеет всё сам: `makePayment()` (`debt.aggregate.ts:221`),
`setForgivenAmount()` (`:252`), `close()` (`:243`). Их не зовёт никто, кроме
тестов. Даже серверный обработчик зачёта обходит их через тот же мешок сеттеров
(`offset-debts.handler.ts:144-148`).

Последствия, каждое воспроизводимо:

- **Неатомарность.** Платёж — это «создать транзакцию» и «обновить долг» двумя
  запросами. Если второй не дошёл, в истории висит перевод, а долг не уменьшился.
  `usePartialPayment.ts:244-251` содержит специальный код на этот случай: он
  отличает «до сервера ничего не дошло» (можно откатить кэш) от «транзакция уже
  легла» (откат соврёт, нужен refetch). Это компенсация архитектуры, а не фича.
- **Правило нельзя проверить на сервере.** Клиент может прислать любой остаток.
- **Правило размножается.** Погашение долга делают пять мест: страница долга,
  список, импорт из Telegram, скан чека, split-expense.

**Прецедент правильного решения уже в репозитории.** Зачёт (`POST /debts/offset`)
и отмена закрытия (`POST /debts/:id/reopen`) сделаны одной серверной транзакцией
через `dataSource.transaction` (`offset-debts.handler.ts:67`,
`reopen-debt.handler.ts:147`). То есть два действия из восьми уже атомарны, а
самое частое — обычный платёж — нет.

### Решение

**`POST /debts/:id/payments`** — платёж как команда, а не как патч.

```
{ amount, accountId, date, forgiveRemainder?, excessCategoryId? }
→ { debt, transactions[] }
```

Обработчик повторяет форму `offset-debts.handler.ts`: одна `dataSource.transaction`,
внутри — `CreateTransactionCommand` для платежа, при переплате вторая запись на
излишек, при прощении информационная запись, затем `debt.makePayment(amount)` и
`debt.setForgivenAmount(...)`, затем `save(debt, manager)`.

**`PATCH /debts/:id` сужается до редактируемых атрибутов:** `name`, `personName`,
`description`, `nextPaymentDate`, `accountId`, `debtType`, `isPrivate`,
`createdAt`, `totalAmount`, `feeAmount`. Производные поля из DTO уходят — их
считает домен.

Это ломающее изменение для всех клиентских путей погашения. В том и смысл: после
него правило существует ровно в одном месте, и `usePartialPayment` сжимается с 266
строк до вызова эндпоинта.

## 2. Данные: два кэша, одиннадцать точек мутации

### 2.1. Плоский список тянет всё

`useDebts` читает `GET /debts` — без фильтров, без пагинации, все долги пользователя
(`debtsApi.ts:89-93`). У него девять потребителей: страница долга, десктопная
панель, люди, дашборд, добавление операции, split-expense, подтверждение импорта.

В проде это 428 долгов на 9 пользователей, из них **391 закрыт**. У самого
нагруженного пользователя 318 долгов и 12 активных: каждый экран, которому нужны
активные долги, скачивает 318 строк ради 12.

Пагинацию когда-то сделали — но только для одного экрана: `useInfiniteDebts`
используется ровно в `useDebtsPageState.ts:84` и больше нигде.

**Решение:** `useDebts(userId, { status })` со скоупом. Потребителям, которым нужны
только активные, — `status: 'active'`. Серверный `GET /debts?status=active`.

### 2.2. Инвалидация нарушает собственное правило проекта

`frontend/CLAUDE.md` предписывает: после любой мутации долга — `invalidateDebtRelated`,
потому что более узкие хелперы оставляют на экране устаревшие балансы. Собственные
мутации `useDebts` инвалидируют только `debtQueryKeys.all`
(`useDebts.ts:86,105,123`) — то есть ровно тот узкий случай, от которого правило
предостерегает. Через них идут `useEditDebt.submit` и переключение приватности.

Отдельно `useSubmitStep` (скан чека) инвалидирует только `debtQueryKeys.list`
(`:139,223`) — долг, созданный из чека, не появится на `/debts`, пока что-нибудь
не обновит infinite-кэш.

### 2.3. Одно действие — две реализации

- **Удаление:** `useDebts().deleteDebt(id)` (оптимистично, узкая инвалидация, без
  тоста) и `useCloseDebt().deleteDebt(debt, userId)` (оптимистично,
  `invalidateDebtRelated`, с тостом). Одно и то же понятие, два разных поведения.
- **Создание:** `useDebts().createDebt` и `useDebtForm().createDebt` (своя
  `useMutation`, без оптимистичного патча), плюс четыре прямых вызова
  `debtsApi.create` в split-expense, import, scan-receipt.
- **Оптимистичный патч:** шесть из одиннадцати точек мутации обходят `debtCache.ts`
  стороной.
- **Зачёт выбрасывает ответ сервера:** `debtsApi.offset` возвращает обновлённые
  долги, `useOffsetDebts.ts:23` их не применяет — только инвалидация.

**Решение:** одна точка входа `useDebtMutations(userId)` в `entities/debt`, за
которой create / update / remove / pay / reopen / offset. Каждая — оптимистичный
патч через `debtCache` плюс `invalidateDebtRelated`. Все одиннадцать мест зовут её.

### 2.4. Производные считаются по нескольку раз, местами по-разному

- **«Просрочен»** — пять независимых реализаций: `DebtCard.vue:43-44` (без проверки
  `is_closed`), `DebtHero.vue:15-20`, `DebtDetailContent.vue:34-38`,
  `groupDebtsByPerson.ts:63-66`, `foldGroupsIntoPeople.ts:44-51`. Изменить
  определение просрочки — значит найти пять мест.
- **«Сколько оплачено»** — `getDebtSplit` вычитает прощённое (`types.ts:40-47`), а
  `useEditDebt.paidAmount` (`:29-31`) — нет. Это не стилистика: у прощённого долга
  правка направления блокируется как у оплаченного.
- **Нетто по человеку** — `foldGroupsIntoPeople` (`entities/debt`) и
  `foldDebtsByPersonName` (`entities/person`). Две реализации одного правила,
  синхронность держится комментарием «знак — тот же, что в foldGroupsIntoPeople».
- **Процент** — `getDebtProgress` и `DebtProgressMeter.share()`.
- **Разница в днях** — `ClosedDebtCard.vue:29-34` (`Math.round`) и
  `foldGroupsIntoPeople.ts:49-51` (`Math.floor`).
- **Маскировка приватного имени** `is_private ? '•••' : name` — четыре копии.

**Решение:** производные живут в `entities/debt/model` рядом с `getDebtSplit`:
`isDebtOverdue`, `maskDebtName`, `daysBetween`, `foldDebtsIntoPeople` (одна,
принимающая плоский список; страница людей — тоже страница, ей можно импортировать
`entities/debt`). Копии удаляются.

### 2.5. Границы camelCase не закрыты

`totalSummary` едет насквозь camelCase (`totalGiven`/`totalTaken`) внутри объекта,
где соседние поля переименованы в `person_name`/`debt_type`
(`debtsApi.ts:119-121`). Курсор пагинации camelCase намеренно и это описано в
CLAUDE.md — оставляем. А вот преобразование snake→camel для шаринга живёт в
`features/share-debts/model/buildSharePayload.ts:44-54`, тогда как правило проекта
требует делать это в `entities/<name>/api/*Api.ts`. Переносим в `debtShareApi.ts`.

## 3. Фичи: границы размыты

### 3.1. `close-debt` — три несвязанных действия под одним именем

Внутри: `useCloseDebt` (на самом деле **удаляет** долг), `useCloseAllDebts`
(погашает все долги человека), `useReopenDebt` (отменяет закрытие). Ни одно из трёх
не «закрывает долг» в смысле «оплачен».

**Решение:** `features/delete-debt`, `features/reopen-debt`, а закрытие всех
переезжает в `features/pay-debt` рядом с одиночным платежом — это один и тот же
платёж, только распределённый по списку.

### 3.2. Оптимистичный патч написан дважды и координируется флагом

`useCloseAllDebts` строит план платежей и сам применяет патчи
(`:96-103`), после чего просит `usePartialPayment` не применять свои —
через `skipInvalidation: true`. То есть ответственность «применить оптимистичный
патч» существует в двух местах, а согласованность держится булевым флагом,
протянутым между ними.

С серверным эндпоинтом платежа это исчезает само: план строится один раз, каждый
шаг — один атомарный вызов, патч применяется по ответу сервера.

### 3.3. Форма долга написана дважды

Создание живёт в `features/add-transaction` (`useDebtForm` + `DebtPanel`),
редактирование — в `features/edit-debt`. Это две независимые реализации одной формы:

| | Создание | Редактирование |
|---|---|---|
| Направление → категория/тип | `useDebtForm.ts:62-64,76` | `useEditDebt.ts:177-183` |
| Валидация | `:49-56` | `:89-98` |
| Выбор человека | `PersonPicker` с автодополнением | голый `UInput` |
| Выбор счёта | на карточке суммы выше | `AccountSelector` в шторке |
| Комиссия | есть, с превью списания | **поля нет вовсе** |

Последняя строка — не стилистика: комиссию, введённую при создании, нельзя
исправить никогда.

**Решение:** `entities/debt/model/useDebtFormModel.ts` — поля, валидация,
направление→категория, комиссия. `useDebtForm` и `useEditDebt` становятся тонкими
адаптерами над ним. `PersonPicker` и `AccountSelector` — в обеих формах.

### 3.4. Одна шторка из восьми сделана иначе

Семь оверлеев долгов построены на `UOverlay` и управляются `v-model`.
`EditDebtDrawer` — единственный, кто принимает `open` / `update:open` и собирает
хром шторки из сырых примитивов `vaul-vue` вручную (направление, ручка, кнопка
закрытия, safe-area, клавиатурный хак), тогда как `UOverlay` существует ровно
затем, чтобы этого не делать: его комментарий говорит, что эта разводка была
продублирована в 13 файлах с разъехавшимися высотами.

### 3.5. Хаптика в трёх слоях, у трёх действий её нет

Вибрация вызывается из композаблов (`useEditDebt`, `useDebtPaymentFlow`,
`useDebtsShare`), из компонентов (`PaymentDrawer`, `CloseAllDebtsDrawer`,
`ShareDebtsDrawer`) и прямо из шаблонов страниц (`DebtsListPage`, восемь мест).
При этом у удаления, отмены закрытия и зачёта её нет совсем. А `DebtCard` и
`ClosedDebtCard` вызывают её сами — и родитель вызывает её же ещё раз на том же
клике.

**Правило:** хаптика принадлежит слою UI — тому компоненту, который обрабатывает
жест. Из композаблов убирается, у трёх действий добавляется, двойной вызов
устраняется.

### 3.6. Тост приватности написан в странице дважды

`useDebtsPageState.ts:334-342` и `DebtDetailPage.vue:104-112` — один и тот же
обработчик с одним и тем же тостом. Единственная мутация долга, у которой тост не
инкапсулирован.

## 4. Экраны: деталь долга существует дважды

Маршруты долгов — единственные, кто не использует `platformPage`
(`app/router/index.ts:212-222`), в отличие от Главной, Счетов и Новой операции.
Вместо этого десктоп собран внутри списка через `MasterDetailLayout` со слотом
`detail`, а слот заполняет `DebtDetailPanel` — компонент, который лежит в
`entities/debt/ui`, но страницей и является: сам делает три запроса
(`useDebts`, `useAccounts`, `useDebtTransactions`), держит своё состояние шторки
действий, сам считает `findClosingRecords`.

То есть карточка долга реализована дважды: маршрутом `DebtDetailPage.vue` и
панелью `DebtDetailPanel.vue`, с двумя независимыми наборами обработчиков одних и
тех же восьми действий. И расходятся они не только формой:

- **«Редактировать» на десктопе не открывает редактирование.** Обработчик
  `handleDetailEdit` (`useDebtsPageState.ts:298-302`) делает `router.push` на
  мобильную страницу долга, где пользователь жмёт «Редактировать» второй раз.
  `EditDebtDrawer` при этом умеет десктопный режим (`EditDebtDrawer.vue:104-107`),
  просто с десктопа его никто не открывает. Поскольку `debts` и `debts/:id` —
  несплитованные соседние маршруты, этот `router.push` размонтирует список
  целиком и теряет валютный фильтр, вкладку статуса, позицию скролла и выделение:
  из них в URL живёт только `person`.
- **После платежа и удаления мобильная ветка уходит на голый `/debts`.**
  `router.replace({ name: DEBTS_LIST })` без query (`DebtDetailPage.vue:73,82`) —
  фильтр по человеку, из которого пользователь пришёл, молча теряется. Десктопная
  ветка в том же сценарии просто снимает выделение и остаётся на месте.
- **`findClosingRecords` считается двумя структурно разными способами:** панель
  отдаёт результат в полезной нагрузке события (`DebtDetailPanel.vue:114`),
  мобильная страница считает его локальным computed (`DebtDetailPage.vue:90`).
- **Переключение приватности продублировано дословно**, вместе с комментарием
  (`useDebtsPageState.ts:334-342` и `DebtDetailPage.vue:104-112`).

Дополнительно: панель игнорирует уже вычисленный страницей `selectedDebt` и
переспрашивает его собственным `useDebts` — третья загрузка тех же данных, причём
из другого кэша (плоский нефильтрованный против пагинированного
отфильтрованного), так что панель и соседние шторки на одном экране могут
показывать разные снимки одного долга. Тест это прямо фиксирует:
`DebtsListPage.spec.ts:603-604` мокает `GET /api/debts` с комментарием «Панель
читает долг не из пагинированного списка, а из `useDebts`».

### Состояние экрана мимо URL

В адресе живёт только `person` (и `type`), причём синхронизация написана руками с
двойной записью: `handlePersonClick` сначала присваивает реф, потом делает
`router.replace`, после чего watcher присваивает тот же реф повторно
(`useDebtsPageState.ts:59-65,229-236`). `clearFilter` (`:242-246`) повторяет тот же
танец. Валютный фильтр, вкладка статуса и выделение в URL не попадают вовсе, и
именно поэтому любая навигация их теряет. `typeFilter` вдобавок применяется только
на клиенте — с собственным `TODO` в коде (`:89-91`).

### Мёртвый код, который грузится каждую сессию

`pages/debts/new/AddDebtPage.vue` — шесть строк редиректа на список. Маршрута
`debts/new` в роутере нет вовсе, страницу никто не монтирует, но она безусловно
стоит в списке предзагрузки (`app/router/prefetchTargets.ts:27,75`) и скачивается
у каждого пользователя при каждой загрузке.

### Мелочи, которые правятся заодно

`DebtDetailPage.vue:163` использует `lg:pb-8` — ровно тот брейкпоинт-класс, который
CLAUDE.md запрещает. Выражение кольца выделения скопировано дословно в двух местах
шаблона (`DebtsListPage.vue:305-309` и `:358-362`). `useDebtsPageState.ts:19`
импортирует `useIsDesktop` из старого шима вместо канонического
`@/shared/lib/platform`.

### Решение

`MasterDetailLayout` остаётся: это настоящий общий примитив, им пользуется и
История, и UI по брифу менять не нужно. Меняется наполнение:

- `pages/debts/model/useDebtsPage.ts` — состояние списка (фильтры, URL, пагинация,
  выбор, сводки).
- `pages/debts/model/useDebtDetail.ts` — состояние карточки долга: данные, действия,
  модалки. Один и тот же композабл питает и маршрут, и десктопную панель, поэтому
  восемь наборов обработчиков схлопываются в один, а расхождения из списка выше
  исчезают вместе со вторыми копиями.
- `DebtDetailPanel` переезжает из `entities/debt/ui` в `pages/debts/detail/` и
  перестаёт ходить за данными: получает готовую модель.
- «Редактировать» на десктопе открывает `EditDebtDrawer` на месте — он это уже
  умеет.
- Возврат после платежа и удаления сохраняет фильтр, из которого пришли.
- Фильтры и выделение переезжают в URL через `useRouteQuery` из VueUse, двойная
  запись уходит.
- `AddDebtPage.vue` и его строка в `prefetchTargets` удаляются.

## 5. Компоненты: карточки-близнецы

`DebtCard` и `ClosedDebtCard` совпадают примерно на 60–65%: одинаковая оболочка
кнопки, кружок с иконкой 9×9, блок имени с маскировкой, обработчик клика с
хаптикой, шаблон aria-label. Различаются осью «состояние»: какая сумма
(`remaining_amount` против `total_amount`) и что снизу (`UProgressBar` против
мини-таймлайна). При этом у `ClosedDebtCard` нет `focus-visible`-кольца, которое
есть у близнеца, и кружок иконки другой формы (`rounded-lg` против `rounded-full`)
без причины.

**Решение:** одна `DebtCard`, различие — состоянием и слотом подвала.

`MutualDebtCard` и `PersonDebtRow` не близнецы: у них другая модель данных и другая
роль. Их оставляем, но `PersonDebtRow` перестаёт рисовать свой аватар вручную там,
где хватает `InitialAvatar` (сплит-градиент для встречных долгов остаётся своим).

Хенд-роллед полосы прогресса в `DebtsSummaryCard`, `MutualDebtCard` и
`ClosedDebtCard` заменяются на `UProgressBar`/`DebtProgressMeter`; хенд-роллед
пилюли — на `UBadge`.

`DebtHero` и `DebtAmountHeadline` не сливаются: первый показывает сумму, второй её
редактирует через `useAmountInput`. Общего — только `tabular-nums`.

## 6. Тесты

Есть у: `useCloseAllDebts`, `useCloseDebt`, `useReopenDebt`, `CloseAllDebtsDrawer`,
`useDebtPaymentFlow`, `usePartialPayment`, `useEditDebt`, `buildSharePayload`,
`renderDebtsCard`, `useDebtForm`, `DebtPanel`, `debtCache`, `foldGroupsIntoPeople`,
`findClosingRecords`, `DueDateField`, обе страницы.

Нет у: `features/offset-debts` целиком, `EditDebtDrawer`, `PaymentDrawer`,
`DeleteDebtModal`, `ReopenDebtModal`, `ShareDebtsDrawer`, `useDebtShare`,
`useDebtsShare`, `view-shared-debts`, `useDebtPaymentForm`, `sortDebts`. Зачёт не
покрыт и на уровне страниц: слова `offset` нет ни в одной из двух спек.

Переработка обязана оставить зелёными существующие спеки (кроме тех, что описывают
удаляемое поведение) и закрыть дыры по действиям, которые трогает: платёж, зачёт,
редактирование, удаление.

---

## 7. Порядок

Каждая фаза самостоятельна, собирается и деплоится отдельно.

1. **Домен и эндпоинт платежа.** `POST /debts/:id/payments`, агрегат через
   `makePayment`/`setForgivenAmount`, зачёт переводится на те же методы,
   `GET /debts?status=active`. Фронт не трогаем — эндпоинт просто появляется.
2. **Данные фронтенда.** `useDebtMutations`, скоуп `status` в `useDebts`, единая
   инвалидация, применение ответа зачёта, производные в одном месте, удаление
   дублей нетто/просрочки/маскировки, перенос трансформации шаринга.
3. **Платёж на новый эндпоинт.** `usePartialPayment` сжимается, `useCloseAllDebts`
   переезжает в `pay-debt`, `close-debt` разбирается на `delete-debt` и
   `reopen-debt`. Сужение `PATCH`.
4. **Форма долга.** `useDebtFormModel`, комиссия и `PersonPicker` в редактировании,
   `EditDebtDrawer` на `UOverlay` и `v-model`.
5. **Экраны.** `useDebtsPage` + `useDebtDetail`, переезд панели из entities,
   схлопывание восьми пар обработчиков, редактирование на десктопе на месте,
   сохранение фильтра при возврате, состояние экрана в URL через `useRouteQuery`,
   удаление `AddDebtPage` и его предзагрузки.
6. **Компоненты.** Слияние карточек, `UBadge`/`UProgressBar`/`InitialAvatar`,
   правило хаптики, `lg:pb-8`, недостающие тесты (включая зачёт).

Фазы 1–2 не меняют поведение вовсе. Фазы 3–6 меняют внутренности при сохранении
UI. Видимых изменений шесть, и все они — исправления: комиссия становится
редактируемой; редактирование на десктопе открывается на месте, а не уводит на
другой экран; возврат после платежа сохраняет фильтр; у удаления, отмены и зачёта
появляется тактильный отклик; у закрытой карточки — кольцо фокуса; из стартовой
предзагрузки уходит мёртвая страница.
