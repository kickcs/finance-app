# Расчёт по долгу: одна связка записей и одна отмена

**Дата:** 2026-10-25
**Откуда:** архитектурный обзор, кандидат 01. Решения Q1–Q3 приняты пользователем, остальные
(R1–R9) — по рекомендации, пользователь поручил реализацию целиком.
**Продолжает:** `2026-08-31-debts-rework-design.md` (§1 платёж командой, §2.3 один писатель).

## 1. Проблема

Платёж по долгу пишет до четырёх записей: ногу отработки, сам платёж (или отметку отработки),
переплату и прощение. Связаны они только одинаковой `date`. Отмена закрытия, удаление
транзакции и два клиентских модуля (`findClosingRecords`, `foldWorkOffRecords`) находят их по
этому совпадению — четыре копии правила. Зачёт ищется ещё хрупче: по пользователю, дате, валюте и
имени человека. Переплата вовсе пишется без `debt_id`, и отмена её не видит.

Следствия, все воспроизводимы по коду:

- Отмена закрытия оставляет переплату в истории — лишний доход или расход.
- Удаление обычного платежа из ленты возвращает деньги на счёт, но не остаток долга.
  Удаление закрывающего платежа оставляет долг закрытым со ссылкой на удалённую запись.
- Правка суммы платежа в ленте меняет баланс, но не остаток долга.
- Долг, участвовавший в зачёте, нельзя удалить: `delete-transaction` на записи зачёта всегда
  отвечает 400, а `delete-debt` идёт без общей транзакции и обрывается на середине.
- Отмена закрытия (кроме зачёта) идёт без общей транзакции.
- «Закрыть все» — зачёт плюс N платежей отдельными запросами с клиента; план считается трижды
  (`useCloseAllDebts`, `CloseAllDebtsDrawer`, `mutualSettlement`), частичный сбой не откатывается.

## 2. Понятие

**Расчёт** — одно действие пользователя, которое меняет остаток одного или нескольких долгов и
пишет записи в историю: платёж (с отработкой, переплатой, прощением), зачёт, «Закрыть все».
Все записи расчёта несут общий `transactions.settlement_id`. Открытие долга и его комиссия —
не расчёт (кандидат 02 обзора). `payment_group_id` — другое понятие («одна операция с двух
счетов»), долговые записи его не принимают.

## 3. Хранение

`transactions.settlement_id uuid NULL`, частичный индекс `WHERE settlement_id IS NOT NULL`.
Ставится только при создании записи и больше не меняется. Отдельной таблицы расчётов нет:
всё, что нужно для отмены, уже лежит в записях (`debt_id`, категория, сумма).

Переплата остаётся без `debt_id`: `debt_id` с недолговой категорией — признак ноги отработки (R8).
Её связь с расчётом — только `settlement_id`.

## 4. Модуль

`backend/src/modules/debt/application/settlement/` — единственный, кто пишет и разворачивает
записи расчётов. Обработчики команд становятся тонкими: разобрать команду, вызвать модуль,
отобразить ответ.

Интерфейс (для обработчиков долгов и `delete-transaction`):

- **платёж** — то, что сейчас делает `pay-debt.handler.ts`, без изменения правил;
- **зачёт** встречных долгов человека в валюте — то, что сейчас делает `offset-debts.handler.ts`;
- **«Закрыть все»** по списку долгов и **предпросмотр** того же плана без записи (фаза 2);
- **отмена расчёта** по его id;
- **отмена закрытия** долга — отмена расчёта, который его закрыл;
- **удаление долга** со всеми его записями.

Внутри: писатель, который ставит `settlement_id` каждой записи и собирает затронутые долги;
чистые функции плана (платёж, зачёт, «Закрыть все») — их тесты табличные, без БД; отмена.
Порядок «старые первыми» везде один: `createdAt ASC, id ASC` (сейчас сервер берёт долги в
порядке репозитория, клиент — по `created_at`, отсюда проверка «Зачёт разошёлся»).

## 5. Отмена

**Состав (R1).** Отменяется расчёт целиком: все записи с его `settlement_id`, каждая со снятием
своего влияния на баланс. Для каждого затронутого долга:

- `applied` = сумма записей расчёта по этому долгу в категориях `debt_return_to_me`,
  `debt_return_from_me`, `debt_offset`, `debt_worked_off` (нога работы не считается — её пара,
  возврат, уже несёт сумму);
- `forgiven` = сумма записей `debt_forgiven` по этому долгу;
- остаток `min(total, remaining + applied + forgiven)`, `forgivenAmount − forgiven`;
- если остаток > 0 — долг открыт: `isClosed=false`, `closedAt=null`, `closeTransactionId=null`.

Правило живёт в агрегате (`Debt.revertSettlement`), а не в `update({...})`.

**Порядок (R1).** Отменить можно только последний расчёт по каждому затронутому долгу:
расчёт S заблокирован, если у любого его долга есть запись другого расчёта, созданная позже
последней записи S. Ответ 409: «Сначала отмените более поздний расчёт по долгу «Имя»».
Для одного долга это всегда так и есть (закрытый долг больше не платится); блокировка реальна
для зачёта и «Закрыть все», которые трогают несколько долгов.

**Атомарность (R9).** Отмена — одна транзакция БД. `DeleteTransactionCommand` получает внешний
`manager` (как уже есть у `CreateTransactionCommand`) и читает запись и счёт через него — иначе
вторая запись на тот же счёт перечитает баланс мимо транзакции и затрёт первую (та же ошибка,
что исправлял коммит 4625c642 для создания).

## 6. Кто зовёт отмену

- **Отмена закрытия** (`POST /debts/:id/reopen`, R2) — расчёт, содержащий
  `close_transaction_id`. Интерфейс и UI не меняются. Закрытый долг без расчёта (старые
  закрытия патчем без записи) открывается с остатком `total − Σ applied` по всем его записям,
  без поиска по дате.
- **Удаление записи из ленты** (R3) — если у записи есть `settlement_id`, отменяется весь
  расчёт (с проверкой порядка). Это заменяет прежние запреты: зачёт, отметку отработки и ногу
  работы теперь можно удалить из ленты — уйдёт весь расчёт целиком. Прежний особый путь «удалили
  прощение — долг переоткрылся» становится частным случаем.
- **Правка записи из ленты** (R4) — у записи расчёта нельзя менять сумму, валюту, тип и
  переводить её в долговую категорию или из неё. Описание, дата, счёт и недолговая категория
  ноги работы правятся.
- **Удаление долга** (R5) — одна транзакция БД. Расчёты, затронувшие и другие долги (зачёт,
  «Закрыть все»), сначала отменяются (с проверкой порядка по другим долгам), затем удаляются все
  записи долга: свои записи расчётов (включая переплату), запись выдачи, исходная запись чека
  (если долг последний), запись комиссии.

## 7. «Закрыть все» (фаза 2, R7)

`POST /debts/close-all` и `POST /debts/close-all/preview` с одним телом:
`{ debtIds, accountId, paymentAmount?, forgiveRemainder?, excessCategoryId?, date? }`.

План повторяет нынешний клиентский: если есть обе стороны — зачёт по переданным долгам (одна
валюта, иначе 400), затем платежи по уцелевшей стороне старыми первыми; переплата уходит
последнему оплаченному долгу; при `forgiveRemainder` недоплаченные долги прощаются. Всё — один
расчёт и одна транзакция БД. Предпросмотр считает тот же план и ничего не пишет. Ответ
исполнения — обновлённые долги, id первой записи платежа (его ждёт подтверждение импорта) и
`settlementId`.

Зачёт внутри «Закрыть все» идёт по переданным id, а не по имени человека: что пользователь
видел одной строкой, то и сводится.

Отмена закрытия любого из этих долгов отменяет всё «Закрыть все» целиком: это один расчёт.

## 8. Миграция старых записей (Q3)

Схема и связка — две миграции. Связка по нынешнему правилу, один раз; после неё в коде нет ни
одного сравнения по дате.

- **Платежи:** записи с `debt_id` (кроме записей, на которые ссылаются
  `debts.transaction_id / source_transaction_id / fee_transaction_id`) в категориях
  возврата, прощения, отметки отработки и нога работы (недолговая категория, не
  информационная) — один расчёт на пару `(debt_id, date)`. Прод: 515 записей → 509 расчётов,
  ни одной пары с двумя возвратами, прощениями или ногами.
- **Зачёты:** записи `debt_offset` — один расчёт на `(user_id, date, валюта долга, имя
  человека)`. Прод: 4 записи, 2 зачёта.
- **Переплаты:** `debt_id IS NULL`, описание `Переплата по долгу: <имя>` — к расчёту последнего
  платежа того же пользователя, того же счёта и того же человека, созданного не позже
  переплаты и не раньше чем за 5 с. Прод: 51 переплата, все 51 находят пару, разрыв ≤ 1,53 с,
  совпадений по времени нет. Старые переплаты лежат с `date`, отличной от платежа, поэтому
  правило идёт по `created_at`.

## 9. Клиент

- `Transaction.settlement_id`; `GET /transactions?debtId=` дополнительно отдаёт записи
  расчётов этого долга без `debt_id` (переплату) (R6).
- `foldWorkOffRecords` группирует по `settlement_id`, записи без `debt_id` в ленту долга не
  попадают. `findClosingRecords` — все записи расчёта, содержащего `close_transaction_id`
  (теперь с переплатой).
- Удаление записи расчёта из истории предупреждает, что уйдёт весь расчёт, и инвалидирует
  через `invalidateDebtRelated`. Правка суммы у записи расчёта недоступна, с подсказкой.
- Фаза 2: `useCloseAllDebts` — один запрос; шторка строит предпросмотр по серверному
  `preview`; `mutualSettlement.ts`, клиентский план и флаг `bulk` в `usePayDebt` удаляются.

## 10. Тесты

Новый `backend/test/debt-settlement.e2e-spec.ts` на настоящей БД (тот же стенд, что у
`analytics-stats.e2e-spec.ts`): платёж → удаление из ленты; переплата + прощение → отмена
закрытия; отработка с категорией → отмена; зачёт → отмена с одной стороны; зачёт + поздний
платёж → 409; удаление долга с зачётом; правка суммы записи расчёта → 400; «Закрыть все» →
отмена; предпросмотр = исполнение. Чистые функции плана — табличные юнит-тесты. Спеки
обработчиков, которые проверяли порядок сырых SQL-запросов, заменяются, а не дополняются.
