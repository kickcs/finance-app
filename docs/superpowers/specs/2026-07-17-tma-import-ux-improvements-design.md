# TMA-импорт: улучшения UX экрана подтверждения

**Дата:** 2026-07-17
**Статус:** дизайн утверждён, ждёт плана реализации
**Контекст:** фидбек после использования Telegram Mini App (`/tma` → инбокс импорта) в проде. Пять проблем: тосты перекрывают кнопку подтверждения, «моргание» экрана между транзакциями, неработающая кнопка «назад», отсутствие обработки кейса «возврат долга», отсутствие балансов счетов для сверки.

Все изменения — только frontend. Backend не трогаем: `POST /api/telegram-import/inbox/:id/confirm` уже принимает произвольный `transactionId`.

---

## 1. Тосты сверху на импорт-страницах

**Проблема.** `ToastViewport.vue` жёстко позиционирует тосты `fixed bottom-0` с отступом `88px` под BottomNav. На импорт-страницах BottomNav скрыт, кнопка подтверждения — внизу формы; тост её перекрывает.

**Решение.** Позиция viewport'а становится управляемой через route meta:

- В роуты `import-inbox`, `import-inbox/:id` (`IMPORT_CONFIRM`) и `scan-receipt` добавляется `meta: { toastPosition: 'top' }`.
- `ToastViewport.vue` читает `useRoute().meta.toastPosition` (computed): `'top'` → классы `top-0` + `pt-[calc(env(safe-area-inset-top,0px)+16px)]`; иначе — текущее поведение (`bottom-0` + отступ 88px).
- `swipeDirection: 'up'` в `ToastProvider.vue` не меняется (для top-тостов свайп вверх на закрытие естественен).
- Анимации появления/исчезновения тоста должны корректно работать для верхней позиции (слайд сверху вниз при появлении).

**Файлы:** `shared/ui/primitives/toast/ToastViewport.vue`, `app/router/index.ts`.

## 2. Устранение «моргания» между транзакциями

**Проблема.** `confirmImported`/`dismissImported` в `entities/imported-transaction/api/useImportedTransactions.ts` делают `onSettled: invalidate` всего ключа `importedTransactionQueryKeys.all` → полный рефетч инбокса. Страница подтверждения берёт `item` через `find` по кэшированному списку; на время рефетча после `router.replace` на следующий `:id` элемент недоступен → мелькает загрузочное/пустое состояние.

**Решение.** Оптимистичное точечное обновление кэша вместо инвалидации:

- В `onSuccess` мутаций `confirmImported`/`dismissImported`: `queryClient.setQueryData` по ключу списка — удалить обработанный элемент из массива. Полную инвалидацию убрать.
- `goNextOrBack()` в `ImportConfirmPage.vue` вычисляет следующий элемент до/независимо от обновления кэша (текущая логика по отсортированному списку сохраняется), затем `router.replace` — данные следующего элемента уже в кэше, страница рендерится без промежуточного состояния.
- Фоновый `refetchInterval: 30_000` остаётся — новые уведомления и серверная консистентность подтягиваются как раньше.

**Файлы:** `entities/imported-transaction/api/useImportedTransactions.ts`, `pages/import-inbox/confirm/ImportConfirmPage.vue`.

## 3. Кнопка «назад» + нативный Telegram BackButton

**Проблема.** «Назад» на экране подтверждения делает `router.back()`; в TMA история пуста или состоит из `replace`-переходов (вход `/tma` → `replace` на инбокс, переходы между подтверждениями — тоже `replace`) → кнопка не делает ничего. Нативная стрелка Telegram не подключена вовсе (`loadTelegramWebApp.ts` не знает про `BackButton`).

**Решение.**

- На `ImportConfirmPage` обработчик «назад» — всегда явный переход в инбокс (`router.replace({ name: IMPORT_INBOX })`) с сохранением slide-back-анимации. Не зависит от истории.
- Интерфейс `TelegramWebApp` в `shared/lib/telegram/loadTelegramWebApp.ts` расширяется: `BackButton: { show(): void; hide(): void; onClick(cb): void; offClick(cb): void }`.
- Новый композабл `useTelegramBackButton(handler)` в `shared/lib/telegram/`: если приложение запущено внутри Telegram — `onMounted` показывает стрелку и вешает handler, `onUnmounted` снимает handler и скрывает стрелку. Вне Telegram — no-op.
- Подключение: `ImportConfirmPage` — стрелка видна, ведёт в инбокс. `ImportInboxPage` — стрелка скрыта (верхний уровень TMA).

**Файлы:** `shared/lib/telegram/loadTelegramWebApp.ts`, новый `shared/lib/telegram/useTelegramBackButton.ts`, `pages/import-inbox/confirm/ImportConfirmPage.vue`, `pages/import-inbox/ImportInboxPage.vue`, `app/router/index.ts`.

## 4. «Погашение долга» на экране подтверждения

**Проблема.** Входящий перевод-возврат долга приходит как обычный `income` (уведомление HUMO не содержит имени отправителя — автодетект по тексту невозможен). Механизм погашения (`makePartialPayment`) в приложении есть, но из флоу импорта недоступен. Существующий долговой путь (`DebtPanel`) создаёт *новый* долг и помечает импорт `dismissed`.

**Решение.** Оба направления:

| Тип импорта | Направление долга | Категория транзакции |
|---|---|---|
| `income` | `given` («мне должны») | `DEBT_RETURN_TO_ME` |
| `expense` | `taken` («я должен») | `DEBT_RETURN_FROM_ME` |

**Ручной путь.** На экране подтверждения для expense/income-импортов — опция «Погашение долга» (рядом с существующим долговым путём). Открывает шторку со списком открытых долгов подходящего направления и валюты импорта (данные — `useDebts`, фильтр `!is_closed`). Элемент списка: имя человека, остаток, валюта.

**Выбор долга →**
1. `makePartialPayment(debt, amount = сумма импорта, accountId = выбранный счёт, ...)` — существующий механизм из `features/partial-payment`: создаёт транзакцию, уменьшает `remaining_amount`, при полном возврате закрывает долг, переплату обрабатывает как excess. Дата транзакции — `occurredAt` импорта (если `usePartialPayment` не принимает дату — расширить options).
2. `confirmImported(importId, { transactionId: <id созданной транзакции>, accountId })` — импорт становится `confirmed` (не `dismissed`), карта мапится на счёт как обычно.
3. Кэш: `invalidateDebtRelated` (стандарт для любых долговых мутаций) + точечное удаление импорта из кэша инбокса (см. §2).

**Автоподсказка.** Если сумма импорта точно равна `remaining_amount` ровно одного открытого долга подходящего направления и валюты — над формой баннер: «Похоже, это возврат долга от {имя} — Применить». Тап по «Применить» выполняет тот же флоу с этим долгом. При нескольких совпадениях или отсутствии точного — баннер не показывается. Логика матчинга — чистая функция (юнит-тесты).

**Файлы:** `pages/import-inbox/confirm/ImportConfirmPage.vue` (+ новые компоненты шторки/баннера в `pages/import-inbox/`), чистая логика матчинга — `pages/import-inbox/model/`, `features/partial-payment/model/usePartialPayment.ts` (опция даты, если отсутствует).

## 5. Лента балансов на экране подтверждения

**Проблема.** На экране подтверждения не видно текущих балансов — нечем сверить корректность импорта.

**Решение.** Горизонтально скроллящаяся лента чипов «Счёт — баланс» под шапкой `ImportConfirmPage`:

- Только нескрытые счета: фильтр по `profile.dashboard_settings.hidden_account_ids` (флага на самом `Account` нет — скрытие живёт в профиле). Данные счетов уже загружены (`useAccounts` используется для селектора).
- Мультивалютные счета показывают баланс в валюте импорта; если баланса в этой валюте нет — основной/первый баланс счёта.
- Чип счёта, привязанного к карте из уведомления (`suggestedAccountId`), подсвечен. Под ним — банковский `balanceAfter` из уведомления со сверкой: если `баланс_в_приложении ± сумма_импорта === balanceAfter` (знак по типу импорта) — ✓, иначе ⚠ с ожидаемым значением. Сверка — чистая функция (юнит-тесты). Если `balanceAfter` в уведомлении отсутствует — строка сверки не показывается.
- Лента видна и в TMA, и в обычном вебе (страница общая).

**Файлы:** новый компонент `pages/import-inbox/confirm/AccountBalancesStrip.vue` (или рядом), чистая логика сверки — `pages/import-inbox/model/`, `pages/import-inbox/confirm/ImportConfirmPage.vue`.

## Тестирование

- Юнит-тесты (Vitest): матчинг долга по сумме/направлению/валюте (§4), сверка `balanceAfter` (§5) — чистые функции.
- Ручная проверка в TMA (прод/стейджинг): тосты сверху, отсутствие моргания при цепочке подтверждений, работа обеих кнопок «назад», флоу погашения долга обоих направлений, лента балансов и сверка.
- `bun run build` (frontend) перед коммитом.

## Вне скоупа

- Парсинг имени отправителя P2P-перевода (в уведомлении HUMO его нет).
- Автосоздание транзакции погашения без участия пользователя.
- Изменения backend (парсер, InboxItem, confirm-endpoint).
- Перевод существующего пути `DebtPanel` (создание нового долга) с `dismissed` на `confirmed` — известный компромисс, отдельная задача.
