# Оплата с двух счетов (payment group)

Одна операция расхода или дохода, проведённая частями с двух счетов: покупка на 100 000,
из которых 60 000 картой и 40 000 наличными. Обе части — обычные транзакции, связанные
общим `payment_group_id`.

## Решения пользователя

- Сценарии: расход и доход на «Новой транзакции», скан чека, подтверждение TMA-импорта,
  редактирование транзакции. Долги, переводы, быстрые действия — вне объёма.
- В истории — две строки (каждая часть отдельно) с пометкой «часть · из 100 000».
- Обе части в одной валюте — валюте операции.
- Разбивка редактируется полностью: смена счетов и сумм, добавить/убрать вторую часть.
- Удаление любой из двух строк удаляет операцию целиком. Убрать одну часть — через правку.

## Терминология

В коде понятие называется **payment group** / **second part**. Слово `split` уже занято
разделением расхода с людьми (`features/split-expense`, `source_transaction_id`) — не
смешивать. В UI: «Второй счёт», «+ второй счёт», «Часть · из N».

## Данные

`transactions.payment_group_id uuid NULL` + индекс (миграция, `synchronize: false`).
У обеих частей группы совпадают `type`, `category_id`, `description`, `date`, `currency`,
`user_id`; различаются `id`, `account_id`, `amount`. В группе ровно две строки.

Ограничения: только `type ∈ {income, expense}`; нельзя для `is_informational`,
`is_debt_related`, строк с `debt_id`, вместе с `feeAmount`; счета частей различны и
принадлежат пользователю; суммы обеих частей > 0.

Балансы, лента счёта, аналитика, бюджеты, `useBalanceAfter`, сверка `balance_after`
импорта работают без изменений — каждая часть списывает/зачисляет свой счёт.

## API (backend camelCase)

**`POST /api/transactions`** — необязательное поле `secondPart: { accountId, amount }`.
`accountId`/`amount` тела — первая часть. Обе строки создаются в одной БД-транзакции
(один `manager`), с новым `paymentGroupId`. Ответ — первая часть с заполненным
`paymentSibling`.

**`PATCH /api/transactions/:id`** — необязательное `secondPart: { accountId, amount } | null`.
- объект: у строки есть пара → пара получает счёт/сумму из `secondPart` (баланс: откат
  старого эффекта, применение нового); пары нет → создаётся с новым `paymentGroupId`,
  который получает и редактируемая строка;
- `null`: пара удаляется (её эффект на баланс откатывается), `payment_group_id` строки
  обнуляется;
- поле отсутствует: изменения общих полей (тип, категория, описание, дата, валюта)
  переносятся на пару, при смене типа/валюты её эффект на баланс пересчитывается.
Смена типа на `transfer`/`adjustment` у строки в группе — 400.

**`DELETE /api/transactions/:id`** — удаляет строку и её пару (оба эффекта на баланс
откатываются в одной БД-транзакции). Запрет удаления по открытому долгу проверяется
для обеих строк.

**Ответ транзакции** (везде, где отдаётся `TransactionResponse`: список, лента счёта,
одиночная, create, update) получает `paymentGroupId: string | null` и
`paymentSibling: { id, accountId, amount } | null`. Пара подтягивается пакетным запросом
по `payment_group_id` для страницы результатов — тем же приёмом, что `returnedAmount`.

## Frontend

**Типы** (`shared/api/database.types.ts`, snake_case): Row + `payment_group_id`,
`payment_sibling: { id, account_id, amount } | null`; Insert + `second_part?: { account_id,
amount }`; Update + `second_part?: { account_id, amount } | null`. Преобразование — только
в `entities/transaction/api/transactionsApi.ts`.

**Форма.** `TransactionFormData` получает `secondPart: { accountId, amount } | null`.
`formData.amount` — всегда **итог операции**; первая часть = итог − вторая.
`useSubmitTransaction` шлёт `amount = итог − вторая`, `second_part`, оптимистично меняет
оба баланса и кладёт в кэш обе строки; откат удаляет группу (сервер удаляет пару сам).

**Чистая модель** `features/payment-group/model`: расчёт частей и валидация
(`вторая > 0`, `вторая < итог`, счета различны), два режима якоря:
- `total` (новая транзакция, чек, правка): итог задаёт пользователь, правка второй части
  меняет первую;
- `primary` (TMA-импорт): первая часть закреплена суммой из банка (сверка по
  `balance_after`), вторая добавляется сверху, итог = банк + вторая.

**UI-блок** `features/payment-group/ui` — переиспользуемый редактор частей: в выключенном
виде тихая кнопка «+ второй счёт»; во включённом — две строки «● Счёт  сумма» (вторая с
выбором счёта, вводом суммы и ✕), пропорциональная полоска в цветах счетов, прогноз
остатка/«не хватает» на каждую часть.

**Экраны.**
- Новая транзакция: блок под суммой на «Расходе» и «Доходе»; при переходе на
  «Перевод»/«Долг» вторая часть сбрасывается.
- Скан чека: блок в секции счёта; итог — сумма чека. Долги участников привязываются к
  первой части.
- TMA-импорт: блок с якорем `primary`; недоступен при пометке «В долг» и для перевода.
  `confirmImported` получает первую часть.
- Редактирование: тот же блок; сохраняется одним PATCH.
- Строка истории: у счёта пометка «часть · из N» (N = amount + sibling.amount).
  Панель деталей: обе части и итог.
- Удаление: текст подтверждения называет обе части.

## Вне объёма

Долги с двух счетов, переводы, быстрые действия, разные валюты частей, больше двух частей.
